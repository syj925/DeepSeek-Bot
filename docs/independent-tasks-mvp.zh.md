# DSH Bot 独立任务记录（2026-11-09）

本次改动位于 DSH Bot 插件。正式桌面现有 Bot 0.1.75 是基线，新插件包版本为 `0.1.76`。未修改 Harness、桌面主进程、用户会话或已安装插件。基线来源见 `bot-baseline-0.1.75-provenance.zh.md`。

## 使用方式

- 用户仍在员工私聊或任务群提出需求。普通问答不生成任务。
- 新任务群在 `create_group(task_objective, task_steps, acceptance_criteria)` 时建立独立记录；私聊的多步骤交付通过 `register_task` 登记。员工应先保存目标、用户要求和计划，再执行。
- 现有信息栏显示关联任务、阶段、已保存检查点、阻塞原因和各版交付。团队栏和拖出的聊天窗口共用这份数据，整体布局和底部即时执行状态不变。
- `complete_task` 将受管任务的交付存为独立版本，状态为“等待你验收”。模型不能替用户验收。
- 用户可以确认验收，或填写修改意见并选择返工起点。返工保存意见、保留旧交付；只有再次点击继续才派发。
- 执行出错或应用重启保留已登记的检查点；由用户选择继续。不会因为对话结束、员工空闲或最后一条回复失败而删除任务记录。
- 本轮复用信息栏，未新增桌面摆件。

## 记录与边界

`state.workTasks` 以 UUID 为键，保存任务修订号、目标、要求、负责人、实际参与员工、必要会话关联、步骤、交付版本和验收状态。员工使用稳定 `botId`；当前执行分段与历史分段分开。Chief 的发起会话仅为来源关联，不因此占据执行任务，也不向其他员工灌入它的私聊。

同一员工可在不同群拥有独立任务。一个执行会话同时只允许一项进行中/阻塞任务；同一群需先验收当前交付，才能开始下一轮。完成任务的历史记录不会被新一轮覆盖。私聊中旧任务待验收时可以处理新任务，但返工/继续会检查是否与当前任务冲突。

阶段状态来自员工调用 `update_task_progress` 保存的工作摘要，不是从字数、模型思考时间或聊天里的“完成了”推测的百分比。默认未提供计划时只有一项交付步骤；多阶段任务应在创建时提供具体步骤。检查点是工作记录，不是自动证明事实正确。

文件留存于 Bot 数据目录 `task-records/<taskId>/versions/<version>/`。只允许实际执行工作目录内的普通文件，拒绝链接路径和越界路径；单文件上限 20 MB、单版总计上限 50 MB。复制、下载和验收会核对哈希。原工作文件后来修改，不会覆盖已经留存的交付版本。信息栏下载留存版本，不依赖员工文件预览器的跨目录权限。

本轮文件检查覆盖存在性、路径、大小与完整性，业务内容质量仍由用户按要求验收；没有把“CSV 已生成”等同“客户都符合定位”。没有新增真实检索源、自动商业事实核验、岗位规则晋升、RAG 或重复工作流识别。新受管任务验收只写结果索引，不把 AI 的检查点直接沉淀成已确认业务规则。已有普通记忆能力保持原样。

继续执行使用原 Bot 的工具、模型和权限；任务记录不扩大授权。恢复提示要求检查已有成果、只做未完成内容，但这不是任意外部工具的 exactly-once 事务保证。外部服务返回不明确时，仍需先核对是否已执行。

## UI 与 API 交接

- `state.workTasks` / `work-tasks`：任务视图。
- `control-work-task`：`taskId`、`expectedRevision`、`action`，可选 `note`、`stepId`。动作 `accept` / `rework` / `resume` / `finalize`；最后一项只补偿已验收任务的索引同步，不执行任务。
- `work-task-file`：仅接受任务 ID、交付 ID、文件序号；不接受任意文件路径。
- 多窗口写入需携带任务修订号，旧版本操作拒绝并刷新。界面只保存选择项和已读状态，不自行判定完成。
- 主组件是 `src/client/work-tasks.js`，由原 `ConversationTaskPanel` 引入。桌面摆件若以后加入，应消费同一记录，不另存任务状态。
- `src/host/work-tasks.js` 负责记录与状态变更，`work-task-integration.js` 连接既有群聊执行、文件留存、结果索引和继续任务。

## 验证

隔离环境使用本地模拟模型，未调用真实付费模型或用户数据。验证覆盖真实员工工具调用、群聊三阶段、检查点、重启、显式继续、过期修订拒绝、返工保留两版成果、人工验收和双 API 客户端一致性。报告保存在本工作树 `.dsh-test-work-tasks-20261109/work-tasks-report.json`。

界面采用真实组件和隔离 Headless Edge，以中文模拟数据检查 400px 信息栏的待验收、阻塞和返工状态，无横向溢出或按钮截断。截图在 `.artifacts/work-tasks-ui/`。这不等于已在用户正在运行的桌面进程部署。

所有旧任务维持原有完成方式；没有批量转换历史聊天。版本文件会占用磁盘空间，本轮不自动删除用户交付。

## 0.1.78 信息栏整理与岗位经验（2026-11-09）

- 任务页仅包含历史任务与相关协作。任务标题可展开查看已保存进度，进行中的记录仍标注真实状态；相关协作只提供该员工关联的群聊跳转入口。
- 成果页包含产出文件与岗位经验。交付版本、验收和返工入口继续保留，待处理页继续承接授权与错误恢复。
- 员工私聊不再选择经验所属人，直接使用当前员工的稳定 Bot ID。群聊按真实成员折叠展示，不默认打开 Chief 的个人经验。
- 岗位经验读取原有 `memory/bots/<botId>/task-lessons.md`，不是把历史任务总结改名显示。用户可以补充、编辑、删除；删除放在更多菜单，变更仍留在原记忆日志。
- `job-experience-view` 读取条目及修订号；`job-experience-save` 接受 `botId`、`revision`、`action`（add/edit/remove）、`entryId` 和 `text`。服务端固定只能写该员工的经验主题，不接受客户端指定路径或团队记忆范围。
- 保存沿用记忆队列、长度与敏感内容检查；在队列内再次检查修订号，避免多窗口覆盖。失败保留编辑草稿，取消后重新编辑可加载最新条目。临时员工不写长期经验，记忆关闭或只读运行时不可修改。
- 保存不额外调用模型。员工可通过现有 `recall` 工具检索修改后的经验；提示词只加入按需检索提醒，不把全部经验重复塞入上下文。
- 沿用已有任务经验提炼能力，没有把每条历史总结或新受管任务的验收自动晋升为经验，也未在本次加入新的 RAG 或工作流沉淀机制。

隔离 Host 验证覆盖实际员工 recall 调用、跨员工隔离、过期版本拒绝、重启持久化和删除留痕。界面验证覆盖私聊/群聊、400px/304px 宽度、三个分类、切换分类保留草稿、请求失败重试和键盘操作；均使用模拟数据。

本版验证：1276 项单元测试通过，构建一致性检查与 lint 通过；隔离 Host 5 项检查和 12 种界面组合通过。2026-11-09 已替换正式桌面 Bot 插件并重启，公开 API 确认为 0.1.78、已启用且无插件错误，原 29 名员工与 6 个群仍可读取。未修改 dev 桌面。部署报告位于工作区 `.artifacts/job-experience-desktop-20261109/`，旧插件与配置已留备份。

## 0.1.79 文件列表恢复与经验来源（2026-11-09）

产出文件恢复图标、文件名、任务名和打开入口的简洁列表；最新交付版本直接列入其中，保持任务 ID 与交付 ID，不误下载其他版本或已变化的原文件。验收、返工及旧版本保留在历史任务的展开详情，待验收数量也移到任务标签。

岗位经验下方只显示“来源：任务名 · 员工名”。点击后展开原任务摘要，有有效会话时提供“打开来源对话”。这是打开对应会话，不承诺定位到某一条聊天气泡。手动经验标记“手动补充”；旧记录无法对应任务时明确标记，不按相似标题猜配。

`job-experience-view` 的条目新增 `provenance`：kind、taskKey、title、author、summary、targetId、edited。任务经验按原 `source: completed task <key>` 与员工 taskIndex 的精确键关联。新提炼经验同时保存任务标题、总结员工、任务摘要、会话标识等元数据；修改已有经验时保留来源，旧经验在可解析时一并留存这些信息。来源摘要只取已有任务记录，不另调用模型补写；缺失摘要不展示为已经记录。正文和元数据仍受现有记忆主题容量限制。

验证：1279 项单元测试通过；隔离 Host 6 项检查通过，涵盖溯源元数据持久化及编辑后保留；12 种布局和文件打开、来源展开、来源会话跳转均通过。构建一致性检查与 lint 通过。
