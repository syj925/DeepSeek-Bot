## 交接目标

请在保留现有业务行为的前提下，改善桌面画布、员工 Dock、聊天窗口和进度/结果呈现的视觉一致性与易读性。可以调整布局、色彩、字体、间距、图标呈现、层级和动效；如需改变点击目标、手势、导航或业务流程，请先把方案作为设计稿反馈给功能负责人，不要直接改变现有语义。

用户最关心的两点是：长任务期间能看懂系统正在做什么、有没有卡住；任务完成后能稳定找到摘要与产物。界面应传达可验证的执行状态，而不是模拟模型的内心思考。

## 本版本应保留的用户行为

### 员工画布与对话

- 每个员工、负责人和群聊继续对应现有真实实体与会话。点击员工进入对应对话；不能用预览数据替代真实联系人、员工或会话。
- Dock 用于组织联系人和部门入口，员工拖入画布、打开对话、建群等操作仍由现有功能实现。部门和员工顺序、身份及目标 ID 必须保留。
- Dock 与团队栏的会话列表解耦，群聊不能变成 Dock 部门入口。总裁办展示 Chief 和各部门负责人；临时员工部聚合在职临时员工，保留长期协调负责人。头像以团队栏中真实员工的已保存形象为准，同一员工不能在不同入口变成不同人物。部门弹层介绍部门职责，不显示最近私聊内容。
- 新用户首次初始化可获得六个正式部门（销售、技术、产品、运营、人事、临时员工部）及 20 位预设员工，另有 Chief；总裁办是管理联系人视图。初始化使用现有后端及 `presetOrganization: true` 配置，UI 不重复造人、不重新灌入已删除预设。执行任务仍需可用模型配置。
- 单聊、任务群和桌面对话浮窗沿用当前会话身份。重做窗口外观时，不得复制出第二个编辑器/会话，也不能丢草稿、附件或跳错会话。
- 保留现有聊天输入、发送、滚动、关闭、缩放/拖动及辅助功能行为。状态展示不得遮挡输入框或抢走聊天焦点。

### 长任务状态（本次重点）

- 正在等待模型、运行工具、生成回复时，聊天区域可显示轻量的友好状态提示；较长等待期间提示会轮换，并可显示已等待时长。
- 有工具调用、等待答复/审批或错误时，现有状态数据能区分这些情况。可重新设计标签、图标和层级，但需保留状态含义、可访问性和实际执行入口。
- 当前动作必须来自真实运行/工具/执行数据。不要用固定百分比、虚构阶段、假进度条或“正在分析第 N 步”等模拟文案；若暂时没有新进展，应明确表达等待，而非暗示仍有实际进展。
- **不要增加模型思维链/内部推理过程展示。** 0.1.59 已从聊天消息流移除了内联“思考过程”展示；友好等待状态和真实执行状态是面向用户的进度反馈，不是思维链。独立的执行详情仍使用已有入口。

### 任务完成、结果与通知

- 已完成任务的摘要以持久、可折叠的结果卡呈现，不能因后续普通消息或员工回执被挤走。默认突出最近结果；展开后查看完整摘要、文件入口及任务群入口（若有）。
- 结果必须来自任务完成记录、正式任务通知或员工任务索引。普通聊天回复或员工空闲状态不能被误判成已完成。
- 任务结果中的文件名可触发已有的文件打开行为；路径仍通过现有数据提供。不得编造文件、路径、交付内容或完成状态。
- 右下角完成通知点击主体可跳转到对应任务/对话；文件操作按钮保留各自目标。通知关闭、已读和过期行为不应因重做样式而改变。
- 任务群的创建、协作、完成、归档和继续沿用原流程。归档不是删除；历史聊天、任务记录和产物保持可访问。

## 建议的视觉方向

- 建立一套共享的颜色、圆角、边框、阴影、字体和间距 token，让画布、Dock、浮动聊天框、任务卡和通知像同一产品。
- 把“正在工作 / 等待用户 / 需要处理 / 已完成”做成容易扫读的状态层级；用文字加图形符号，不只依赖颜色。
- 聊天区优先保留消息阅读空间；状态条短而稳定，展开详情时再呈现更多信息。结果卡可折叠，但完成标识、任务标题和一行摘要应始终可见。
- 动效使用短时、低位移的过渡；遵守 `prefers-reduced-motion`，避免持续闪动、布局跳跃和大面积模糊导致的卡顿或对比度问题。
- 亮/暗主题、不同壁纸、窗口宽度和系统缩放下都要检查可读性。半透明表面必须在真实画布背景上验证，不能只看单一静态截图。

## 开发与验证

在隔离副本内操作，不要直接连接真实用户配置或会话。依赖和测试环境准备方式：

```sh
cd ds-bot
npm ci
npm run harness
```

完成客户端修改后运行：

```sh
npm run build
node scripts/build-client.mjs --check
npm test
npm run lint
```

`npm run harness` 只安装测试依赖，`npm run build` 只生成插件前端，两者都不会启动预览网页。测试依赖版本由 `dev/harness/package.json` 固定为 DSH `0.2.0-rc.2`。实际预览需要兼容宿主；沿用 `CONTRIBUTING.md` 的隔离 mock bench，`dev/bench.sh` 还需要兼容的 shell、pnpm 和 DSH 源码环境（Windows 建议按现有 WSL 环境配置）。不要自行写一个只有静态数据的页面并当成真实功能验收。打包插件可在验证通过后运行 `npm pack`，通过兼容宿主的公开插件安装入口加载；它不是桌面安装器。

基线 `675af14` 的验证结果：959 项测试通过，构建产物一致性通过，lint 通过（仓库仍有既存告警）。设计分支的回归不能把旧基线结果当作本次结果；请附上本分支实际运行的命令、测试总数和告警状态。客户端改动一般不要求真实模型调用；需要预览时使用独立 mock/test profile，不要清理、迁移或写入用户正式数据。

代码规范：UI 模块在 `src/client/`，`client.js` 是生成文件；用户文案维护英文键和中文翻译；沿用项目现有 JavaScript/React 代码风格和公开 API。提交时请包括源文件和重新生成的 `client.js`，不要把 `node_modules`、测试 profile、日志、密钥或用户数据放入交付包。
