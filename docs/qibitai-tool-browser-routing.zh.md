# 员工上下文、工具检查与浏览器路由

[English](qibitai-tool-browser-routing.md)

本文说明 0.1.59 的实现边界。源码中的入口不等于发布、安装或真实工具连接已经完成；是否能够操作浏览器，应在对应执行会话中验证实际工具调用。

## 同一个员工，分别执行

员工私聊、群 A 中的该员工、群 B 中的该员工，分别使用自己的执行 Session。一个群的全文不会自动复制到另一个群或私聊。员工身份、已保存的模型、指令、长期记忆与权限策略仍属于同一个 Bot；群成员关系与画布布局不会改变这些归属。

这不是隐私沙箱。Bot 可以按任务需要调用 `read_own_chat`、`read_group_chat` 和 `read_task_history` 查询自己的历史、群记录和任务结果。分开的执行上下文减少无关内容常驻，不阻止已有权限允许的检索。

私聊的“最近群工作”复用员工任务索引、已保存的群任务结果和群回复通知，最多展示最近六条，并提供原群与可用成果文件的入口。普通回复明确标为“已在群里回复”，不会冒充任务完成；原群已经删除时保留摘要，不提供失效的跳转。这个面板不会向模型自动注入完整群讨论。

## 工具检查的四种快照

从当前会话的 **工具与浏览器** 打开检查面板。群聊按成员显示实际执行 Session，私聊显示该员工的私聊 Session。入口只读取已存在的 Agent，不会为了检查而激活它，不会等待能力挂载完成，也不会自动轮询；需要时点击 **刷新工具**。

| 栏位 | 数据含义 | 不能由此认定 |
| --- | --- | --- |
| 已注册工具 | 当前 Agent 可见注册表中的工具 schema 名称 | 这些 schema 全都按原样发给了模型服务商 |
| 最近模型请求 | Session 最近一次组装的请求头中的工具名称 | 服务商最终收到的 wire payload 与它完全相同 |
| 初始工具历史 | Session 历史里的初始工具声明 | 当前仍然加载着全部历史工具 |
| 新增工具历史 | Session 历史中后来追加的工具声明 | 当前刚发生了加载，或工具连接已经可用 |

四栏分别保留 `deferLoading` 标记。它表示该份声明采用按需加载，不能单凭这个标记判定工具丢失。PTC／代码工具模式还可能把能力通过 `run_code` 等入口提供给模型，因此顶层请求中没有逐个列出浏览器工具名，也不直接等于浏览器能力不存在。

“Agent 未激活”“尚未启动”“不可用”描述本次无法读取的状态，不是“该 Agent 有零个工具”。员工能力包的挂载状态另列显示，属于员工范围，不是某一次模型请求的加载结果。挂载显示就绪也不能代替实际调用验收。

面板只展示名称、状态和必要的 Session／预设标识，不展示工具参数 schema、描述、插件配置或凭据。未知会话、非所属员工与非群成员的请求会被拒绝。

### 看起来只有 `read_browser` 时怎样区分原因

1. 确认完整插件已经安装并启用。兼容的 QibitAI Desktop 预装完整浏览器插件 `dsh-builtin-browser`，Windows 还提供 `dsh-computer-use-win`。这两个插件与 DS Bot 的附加页面阅读器不同。
2. 对比底座普通 Agent 与出问题 Bot 的预设、当前注册工具和员工能力挂载。安装存在、预设可见、权限允许是分别需要核实的条件。
3. 若注册表有完整工具，继续看最近组装请求、历史声明、`deferLoading` 与代码工具模式；不要因为顶层只看到一个入口就强制全量加载。
4. 若工具已可见但调用失败，检查目标执行 Session、页面 guest／自动化连接与权限审批。尤其在画布全局页面中，工具注册完整不代表原生浏览器已获得可操作的页面。

这些步骤用于定位问题；仅凭模型的一句“我只能看网页”或一次静态工具列表，不能确认是哪一层失败。

## 完整操作浏览器与附加阅读器

### 底座原生操作浏览器

**工具与浏览器 → 选择群成员 → 打开操作浏览器** 路由到该员工真正执行任务的 Session。私聊使用私聊 Session；群聊要求明确选择成员，只有这个显式打开动作才会通过原有的 `ensureGroupSession` 流程准备缺少的群执行 Session。只做检查不会创建它。

插件随后切换到该 Session 的经典 Agent 视图，等待底座公开 Sidebar 的 `ready` 与 `mounted` 都指向目标 Session，再复用已有 Browser 标签页或创建一个新标签页；支持浮窗时请求浮窗。打开期间切换或返回会取消旧请求，避免旧结果重新抢回导航。**返回 Bot** 回到原来的员工或群。

这条路径使用公开的 `sidebarRight` 接口，没有新建第二套网页自动化环境。提示“浏览器标签页已打开”仅确认 UI 标签页，不证明页面 guest 已获得、自动化已连接或某项操作成功。工具仍由底座完整浏览器插件提供。

目前公开宿主接口要求先显示所属 Session，才能为它创建原生浏览器标签页；Bot 画布是全局页面，不是每个隐藏 Session 的 Sidebar 承载区。因此本次没有把多个隐藏 Session 的原生网页同时嵌入画布。也没有调用宿主私有全局变量或自行创建 `webview` 来冒充真实工具页面。

### 旧版 Bot 页面阅读器

附加阅读器需要宿主提供其独立 Desktop bridge，现代底座不一定包含；缺失时显示不可用。它的 `read_browser` 读取可见页面文字、地址、链接与控件，是额外的只读工具。它不会注册、替代或限制完整底座浏览器工具与电脑工具。

该阅读器可作为画布上的可移动、可缩放浮窗。窗口绑定打开时的员工与群／私聊，不跟随后续选中的会话变化；选中的标签页也按“员工 + 来源群或私聊”记录，防止读到另一个群当前选中的页面。

同一员工的阅读器标签仍使用同一个登录分区，因而共享 cookie 和登录态。群与私聊的标签选择分开，不等于任务之间拥有独立账号环境；不同员工的分区另行区分。这里的规则只针对旧阅读器，底座原生浏览器遵循其自己的 Session 与分区规则。

## 浏览器并行与共享电脑

Bot 是独立员工身份和执行上下文，不会自动获得独立电脑、虚拟机或沙箱。电脑控制操作的是宿主允许访问的桌面；多个员工操作同一桌面仍可能互相干扰，本次插件没有新增全局独占调度。

浏览器可以有多个页面和多个执行 Session，但多个标签页不天然代表 cookie、账号或文件系统隔离。实际可并行范围由底座浏览器插件的页面归属、连接与权限决定。原生浏览器入口解决“查看哪个员工正在操作哪个执行页面”的路由，不承诺多个隐藏原生 guest 已可在画布并排运行。
